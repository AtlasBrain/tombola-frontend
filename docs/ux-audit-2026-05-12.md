# UX audit — 2026-05-12

Scanned every page, traced common journeys, counted clicks. Findings
grouped by impact, with click-saves and effort estimates. Numbers are
**clicks saved per occurrence**, not absolute time.

## Confirmed redundancies

### R1. `/u/[handle]` vs `/creator/[address]` are the same person, two pages
Both render data for a single wallet. `/u` shows "what I won, who I am";
`/creator` shows "pools I run". A viewer clicking a wallet has to know
which page they want. Internal links use `/u/`; private-pool-page's
"CREATOR" link uses `/creator/` — same person, different routes.

**Fix:** Merge `/creator/[address]` into `/u/[handle]` as a tab.
Default tab = OVERVIEW (current /u). New tab = CREATOR (current
/creator content). Redirect `/creator/[address]` → `/u/[address]?tab=creator`.

**Click save per occurrence:** 1 + removes a class of "wrong link"
mistakes.
**Effort:** 1 dev-day.

### R2. Homepage's 3 overlapping "pool feed" sections
`/` has, in order:
1. **Public pools** — current rounds grid (PoolCard × 4)
2. **Recently played on Tombola** — mock event feed (RecentWinners)
3. **All rounds** — table of every pool (AllRoundsTable)

Sections 2 and 3 partially answer the same question ("what's happening
in pools"). Section 2 is currently mock-only — it's a stub.

**Fix:** Drop RecentWinners (mock placeholder). Re-introduce as a real
feed later under "Activity" on the user profile or as a small ticker
at the bottom of the public-pools section.

**Effort:** 30 minutes (delete the import + section).

### R3. CreatePool success screen *and* admin page both host the
INVITE FRIENDS tab
This is intentional and correct — the admin page is the long-lived
surface. But the success screen's tab body is a near-clone. Both
already render the shared `<InviteFriendsTab>`. **No action needed**
— this is shared correctly.

### R4. "Notifications" exists only as a dropdown
There's no `/notifications` route. If a user dismisses the bell, they
have to re-open it to find an old notification. Old notifications scroll
out of the 100-entry cap silently.

**Fix:** Add a "View all" link at the bottom of the bell that opens
`/notifications` — a full-page list with filters (all / unread / kind),
mark-all-read, and individual delete. Reuses the existing notification
data; only new code is the page wrapper.

**Click save:** 2 (find old notif).
**Effort:** 4 hours.

## Friction points (in order of pain)

### F1. Mobile users have no SEARCH and no MY PROFILE button
The `<SearchPaletteHost>` trigger is `hidden sm:inline-flex`. The
`<MyProfileButton>` is `hidden ... sm:inline-flex` AND only renders when
connected. The mobile menu re-renders the same `<MyProfileButton>` —
but with the same `hidden sm:*` class, so it stays hidden inside the
dropdown too. **Net: on phones, the only path to search or your own
profile is the `/` keybind, which mobile users don't have.**

**Fix:**
1. Drop `hidden sm:*` from MyProfileButton when rendered inside the
   mobile dropdown.
2. Add a search trigger to the mobile dropdown (icon button or full
   row).

**Click save:** Massive — without this, mobile users literally can't
navigate to their own profile.
**Effort:** 1 hour.

### F2. First wallet connect has no onboarding
After Connect + sign:
- User has no pseudo claimed
- Search doesn't find them
- WalletLink everywhere shows their raw address
- They have to discover the profile page on their own and click Edit

**Fix:** Detect first-time connect (no profile row exists for this
wallet). Show a one-shot toast or small modal: "Welcome! Want to claim
a pseudo so friends can find you?" with Skip / Set up. Single-use,
remembered in localStorage so it never re-prompts.

**Click save:** ~5 (no need to discover profile + edit flow).
**Effort:** 3 hours.

### F3. Adding a friend takes too many clicks
Current: ⌘K (1) → type → click result (2) → /u/[handle] → ADD FRIEND
(3) → sign (4). Four discrete actions for a one-button feature.

**Fix:** Inline "+ Add" button on each search-palette result row.
Click = signature popup directly. Result stays selectable for
profile navigation if the user wants context first.

**Click save:** 2 per add.
**Effort:** 2 hours.

### F4. Pending friend requests don't badge on the profile button
The bell shows a global count. The MyProfileButton in the header
doesn't show "1 pending" — users have to open the bell or visit their
profile to know they have requests.

**Fix:** Subscribe MyProfileButton to the same friend-list cache the
listener uses. Render a small mint dot or "1" badge on the avatar
when `pendingIn.length > 0`.

**Click save:** Discoverability — converts a "you might miss it"
into a "you can't miss it".
**Effort:** 1 hour.

### F5. CreatePool form has no help / inline explainers
"Codes" field has no description. New creators don't know whether 10
or 100 is right. "Fee %" similarly opaque.

**Fix:** One-line tooltip per input (already a pattern in the
`<MiniStatInput>` component — just unused). Add the help texts.

**Click save:** ~3 (avoids: create wrong, delete, recreate).
**Effort:** 30 minutes.

### F6. Devnet SOL — users get stuck with 0 balance
There's a faucet at `/claim/[code]` but nothing surfaces it on first
connect. Users with 0 SOL who hit "Buy" get a confusing tx-rejection.

**Fix:** Detect 0 SOL on connect; show a banner "Need devnet SOL?
Claim from faucet" with a link/button. (On mainnet rotation: replace
with "buy SOL" / "bridge from CEX" hint instead.)

**Click save:** ~5 (no panic + no Discord support needed).
**Effort:** 2 hours.

### F7. No "back" affordance from per-pool admin
`/create/my-pools/[pubkey]` has no "← Back to pools" link. Users must
hit browser back or use the header logo.

**Fix:** Add `← All my pools` link top-left, mirroring `/u/[handle]`'s
`← All pools` pattern.

**Click save:** 1.
**Effort:** 5 minutes.

### F8. The "PRIVATE" header item routes to `/create`
For someone who's never created a pool, the label is misleading. They
click PRIVATE expecting to browse private pools (which doesn't exist
as a public listing — invites only). They land on a creator dashboard.

**Fix options:**
- (a) Rename header item to "CREATE POOL" (clearer intent).
- (b) Add an explainer banner on `/create` when no pools exist:
  "Create your first private pool — gated by invite codes you control."

I'd do **both**. Effort: 15 minutes.

### F9. Hard-to-find: "where are MY pending friend requests?"
The current placement (inside the amber block on `/u/me`) requires
the user to:
1. Notice the notification (if bell open)
2. Navigate to own profile
3. Scroll to find the amber block

**Fix:** The MyProfileButton badge (F4) + the notification listener
(already exists) cover this. Plus, the bell row already has a `href`
to `/u/[requester]` for each request, so single-click decline can
also live in the bell-dropdown row, not only on the profile page.

**Click save:** 1-2.
**Effort:** 3 hours.

### F10. Empty states are inconsistent
Some are "Loading…" → "No friends yet — try search". Others are
silent (RecentBuysTable when there are 0 buys shows nothing). Some
suggest an action, others don't.

**Fix:** Pass every empty state through a quick audit. Each one should
say what + suggested action. Already half-done.
**Effort:** 2 hours.

## Recommended order of execution

These are ordered by `(click_save × occurrence_rate) ÷ effort`. Top of
the list = best ROI.

| Rank | Fix | Why |
|---|---|---|
| 1 | **F1** mobile search + profile button | Catastrophic gap; cheap fix |
| 2 | **R1** merge `/creator` into `/u` | Kills a redundancy + a confusion class |
| 3 | **F4** pending-request badge on profile button | Hot-path discoverability |
| 4 | **F2** first-connect onboarding | Compounds with every later feature |
| 5 | **F3** "+ Add" inline in search results | High-frequency action |
| 6 | **F6** 0-SOL faucet banner | Onboarding ditch saver |
| 7 | **R4** `/notifications` page | Power-user need + scales for future |
| 8 | **R2** drop the mock RecentWinners section | Cleanup, fast |
| 9 | **F5** CreatePool inline help | Easy comprehension win |
| 10 | **F8** rename PRIVATE → CREATE POOL + banner | Naming clarity |
| 11 | **F7** back-affordance on admin page | Minor polish |
| 12 | **F10** empty-state audit | Polish sweep |

## Where this lands

Items 1-6 are the high-impact bundle — collectively they fix the most
glaring "user gets stuck" or "user can't find" scenarios. About **2
dev-days** total. Everything below is polish.

Items 7-12 are nice-to-have. If you want to ship one wave, do 1-6.
